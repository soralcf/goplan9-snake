# 补码、整数溢出与 AbsDiff 契约（M1）

> 关联代码：`internal/arith/arith_arm64.s`、`internal/arith/arith_test.go`
> 关联笔记：[M1-NOTES.md](M1-NOTES.md)
> 结论：本项目采用**契约 A（32 位二补码回绕）**。`AbsDiff` 的函数注释和测试固定用例共同定义这一行为。
> 状态（2026-11-23）：已实现并通过 `TestAbsDiff`。

## 1. 问题从哪来

`AbsDiff(a, b)` 的定义是 `|a − b|`，参数和返回值都是 `int32`。`int32` 的范围是：

```text
MinInt32 = -2^31     = -2,147,483,648
MaxInt32 =  2^31 - 1 =  2,147,483,647
```

有两个数学结果装不进去：

1. `|MinInt32| = 2^31`，比 `MaxInt32` 大 1；
2. `|MaxInt32 − MinInt32| = 2^32 − 1`，远远超出 `int32`。

所以“溢出时返回什么”不能由实现顺手决定，必须写成**契约**，并由测试钉住。它不是 bug，而是公开行为。

## 2. 圆盘图：一次看懂二补码

把 32 位整数想象成一个有 `2^32` 个刻度的圆盘，刻度值就是无符号二进制：

- 12 点：`0x00000000`，十进制 0。
- 顺时针（正数区）：1、2……直到 `0x7FFFFFFF`（`MaxInt32`），紧挨着 6 点。
- 6 点：`0x80000000`。按无符号读是 2,147,483,648，按有符号读是 `MinInt32`。
- 从 0 逆时针退：第一步是 `0xFFFFFFFF` = −1，继续退到 6 点就是 `MinInt32`。

| 位模式 | 有符号 int32 | 无符号 uint32 | 圆盘位置 |
|---|---:|---:|---|
| `0x00000000` | 0 | 0 | 12 点 |
| `0x7FFFFFFF` | `MaxInt32` | 2,147,483,647 | 6 点顺时针一侧 |
| `0x80000000` | `MinInt32` | 2,147,483,648 | 6 点 |
| `0xFFFFFFFF` | −1 | 4,294,967,295 | 12 点逆时针一侧 |

三个直接结论：

1. **负数比正数多一个**：0 占了正数区的起点，`0x80000000` 只能归负数。
2. **最大正数加一变最小负数**：从 `0x7FFFFFFF` 顺时针再走一步，跨过 6 点就是 `0x80000000`。
3. **最小负数取负还是自己**：取负相当于沿 12–6 点中轴线翻转，而 `0x80000000` 正好在中轴线上。

二补码取负的公式是 `-x = ^x + 1`（超出 32 位的进位丢弃）。代入 `MinInt32`：

```text
0x80000000 取反 → 0x7FFFFFFF
0x7FFFFFFF 加一 → 0x80000000
```

结果绕回自身。注意这里的分工：`MinInt32 − 0` 本身没有溢出；溢出发生在**取负**那一步，因为数学上的 `+2^31` 在 `int32` 里不存在。

> 原笔记里的 `JA/JB`、`OF`、`cdq` 是 x86 视角。arm64 对应关系是：有符号比较用 `BLT`/`BGE`（N/V 标志），无符号比较用 `BLO`/`BHS`（C 标志），符号扩展用 `SXTW` 或 `MOVW`。本项目的 `AbsDiff` 只需要 32 位减法加有符号比较，不需要显式读溢出标志。

## 3. 四条工程口诀

1. **边界长相**：`0x7FFF...` 是最大正数，`0x8000...` 是最小负数，`0xFFFF...` 是 −1。
2. **求反加一**：`-x = ^x + 1`，按 32 位取模，最高位的进位扔掉。
3. **溢出是回绕**：32 位有符号加减乘在 Go 里是确定性的 modulo 2^32，不是未定义行为，也不是随机垃圾值。
4. **要精确先宽化**：需要真实大小时，先转成 `int64` 再相减、取绝对值；不要在同一段逻辑里一半回绕、一半宽化。宽化属于契约 B，不属于契约 A。

## 4. AbsDiff 的两种溢出契约

### 契约 A：32 位二补码回绕（本项目采用）

**定义**：`a − b` 和取负都按 32 位二补码完成，结果按 `int32` 解释。

```text
d = a - b          // 32 位，溢出即回绕
if d < 0:
    d = -d         // 同样 32 位；对 MinInt32 取负仍得到 MinInt32
return d
```

边界行为：

| a | b | 真实差值 | 结果 | 原因 |
|---|---|---:|---:|---|
| `MinInt32` | 0 | 2^31 | `MinInt32` | 取负绕回自身 |
| 0 | `MinInt32` | 2^31 | `MinInt32` | 同上 |
| `MaxInt32` | `MinInt32` | 2^32−1 | 1 | 截断成 −1，取绝对值 |
| `MinInt32` | `MaxInt32` | 2^32−1 | 1 | 同上 |
| `MinInt32` | −1 | `MaxInt32` | `MaxInt32` | 真实差刚好装得下，精确 |
| `MaxInt32` | −1 | 2^31 | `MinInt32` | 32 位截断成 `MinInt32`，取负仍回绕 |
| `MinInt32` | 1 | −(2^31+1) | `MaxInt32` | 32 位截断成 `MaxInt32`，正值保持不变 |

性质：

- 真实差值 `≤ MaxInt32` 时结果精确。
- 结果不保证非负：`MinInt32` 角落会返回负数。
- 极值处不单调：最远的两点相减反而得到 1。
- 实现最省：一次 32 位减法、一次有符号比较、一次条件取负，不需要宽化。

arm64 视角：用 `SUBW` 做 32 位减法，`CMP` 后按有符号条件（`BLT`/`BGE`）决定是否 `NEGW`；也可以用条件选择 `CSNEG` 做成无分支。关键不是具体指令，而是**所有操作保持 32 位宽度、比较使用有符号条件码**。

**为什么中间结果必须保持 32 位**：如果先用 64 位算出精确差，再取绝对值、最后用 `MOVW` 截断，大多数用例结果相同，但 `AbsDiff(MinInt32, 1)` 会得到 `-2147483647`，而契约 A 要求 `MaxInt32`。原因是精确差是负数，64 位取绝对值后截断到 `0x80000001`；契约 A 则先在 32 位把差截断成 `0x7FFFFFFF`，它已经是正数，不再取负。测试里的 `min minus one wraps to max` 就是用来抓这个错误的。

### 契约 B：饱和

**定义**：先用 64 位算出精确的 `|a − b|`，超过 `MaxInt32` 时返回 `MaxInt32`。

```text
d = abs(int64(a) - int64(b))
if d > MaxInt32:
    d = MaxInt32
return int32(d)
```

边界行为：

| a | b | 真实差值 | 结果 |
|---|---|---:|---:|
| `MinInt32` | 0 | 2^31 | `MaxInt32` |
| `MaxInt32` | `MinInt32` | 2^32−1 | `MaxInt32` |
| `MinInt32` | −1 | `MaxInt32` | `MaxInt32`（精确） |
| 普通小范围输入 | 普通小范围输入 | 小 | 精确值 |

性质：

- 结果始终非负，且对差值单调。
- 语义更接近数学定义，适合通用工具函数。
- 需要宽化到 64 位或额外比较封顶，指令更多。

### 两种契约对比

| 维度 | 契约 A：回绕 | 契约 B：饱和 |
|---|---|---|
| 结果范围 | 可能为负（`MinInt32` 角落） | 始终非负 |
| 极值单调性 | 不单调 | 单调 |
| 实现成本 | 低，全 32 位 | 较高，需宽化或封顶 |
| 调用方风险 | 边界输入会得到“意外”的小值或负值 | 封顶值可能被误当作精确值 |
| 适用场景 | 输入范围已知很小 | 通用库、语义优先 |

### 本项目的选择

`AbsDiff` 的调用方只有棋盘坐标：`0 ≤ x < W`、`0 ≤ y < H`，W/H 最多几百。差值远小于 `MaxInt32`，回绕不会发生，契约 A 的精确性与低成本都满足需求。

因此：

- `arith.go` 的函数注释声明“32 位二补码回绕、不做溢出保护”；
- `TestAbsDiff` 用固定用例钉住三个契约角落；
- 如果未来要接受任意 `int32` 输入，应显式升级为契约 B，并同步修改注释、测试和调用方预期——这是一次公开行为变更。

## 5. 测试如何钉住契约

`TestAbsDiff` 分四层：

1. **常规与符号**：相等、正负、异号，验证 `|a−b|` 的基本定义。
2. **精确边界**：`MaxInt32 − 0`、`MinInt32 − (−1)`，验证“装得下就必须精确”。
3. **契约角落**：`MinInt32` 取负绕回自身、双极值相减塌缩成 1。
4. **符号翻转**：`MinInt32 − 1` 等用例，抓住“64 位精确相减再取绝对值”的错法。

随机对拍可以验证常规路径，但几乎抽不到 `MinInt32` 这类极值，所以**固定用例不可省略**。参考实现可以直接写 `d := a - b; if d < 0 { d = -d }`：Go 规范保证有符号溢出按二补码回绕，因此它和契约 A 完全同构。

实现阶段，`TestAbsDiff` 曾保持红灯：占位实现返回 0，只有期望 0 的相等用例会偶然通过。实现后全绿。相等用例的“通过”不能说明实现正确，失败日志里的非零用例才是有效信号。

## 6. 速查

```text
AbsDiff(MinInt32, 0)        == MinInt32   // 取负绕回自身
AbsDiff(MaxInt32, MinInt32) == 1          // 2^32-1 截断成 -1
AbsDiff(a, b) 精确         当且仅当 |a-b| <= MaxInt32
需要真实距离时：用 int64，或换成饱和契约
```
