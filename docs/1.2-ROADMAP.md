# 学习路线与验收标准

本文把项目拆成 M0–M8 九个里程碑。每个里程碑都给出：

- **目标**：这一步要解决什么问题。
- **学习点**：你应该掌握的 Go 汇编/系统知识。
- **任务**：需要你亲手实现的内容（不提供实现代码）。
- **验收**：可执行的检查命令 + 功能检查。
- **常见坑**：这个阶段最容易浪费时间的点。

完成一个里程碑后，再进入下一个。M6（BFS）可以在 M5 之后与 M8 的部分打磨并行，但建议不要跳过 M5 的“保证通关”基线。

> 进度、条目顺序和证据以 [2.1-CHECKLIST.md](2.1-CHECKLIST.md) 为准；本文只保留里程碑目标、学习点、验收口径和常见坑。任务级复选框不再放在这里。

```
M0 工程骨架/ABI0
  -> M1 基本功
  -> M2 系统调用/终端
  -> M3 游戏状态/移动
  -> M4 渲染/主循环
  -> M5 Hamiltonian 保证通关
  -> M6 BFS 独立验证
  -> M7 安全窗口混合策略
  -> M8 打磨/最终验收
```

建议节奏：M0–M2 约 3–5 天，M3–M5 约 4–6 天，M6–M7 约 5–8 天，M8 约 2–3 天。按自己的时间调整，但每个里程碑都要留下验收证据。

---

## 总体验收口径

“完成”不是“能跑起来”，而是同时满足：

1. **功能**：该里程碑定义的行为在真实终端/测试中可复现。
2. **正确性**：边界条件、环缓冲、终端尺寸、系统调用错误路径都有测试或明确处理。
3. **汇编纯度**：该阶段计划放进汇编的逻辑，没有偷偷用 Go 实现。
4. **可解释**：关键指令、数据布局和算法不变量在笔记中有记录，能随时查回并讲清楚。
5. **可回归**：`go test ./... -count=1` 和 `go vet ./...` 保持通过。
6. **文档一致**：`./scripts/check-docs.sh` 通过；进度只写在 `2.1-CHECKLIST.md`。

测试是为了让你敢改汇编。每个里程碑都要有“改动后能快速验证”的测试，而不是最后一次性补。

## M0 — 工程骨架与 ABI0 热身

实现与验收记录：[4.1-ENGINEERING-NOTES.md](4.1-ENGINEERING-NOTES.md)；条目状态见 [2.1-CHECKLIST.md#m0](2.1-CHECKLIST.md#m0)。

### 目标

建立最小可构建的 Go + Plan 9 汇编工程，打通“Go 调用汇编、汇编返回结果”的完整链路。

### 学习点

- `TEXT`、`SB`、`FP`、`PC`、`RET` 的含义。
- ABI0：Go 调用汇编函数时，参数/返回值在栈上的布局。
- `$帧大小-参数大小` 注解，以及为什么是 `$0-24` 这类写法。
- `NOSPLIT` 与 `textflag.h`。
- `go tool objdump` 查看真实指令；`go vet` 检查汇编声明。
- Go 定义的汇编函数在 objdump 中显示为 `包路径.foo.abi0`（例如 `goplan9snake/internal/arith.Add.abi0`），以及编译器生成的 ABI 包装。

### 任务

1. 初始化仓库与模块（模块名用 `goplan9snake`；不能带 `-`，否则汇编无法引用跨包符号）。
2. 创建最小入口：Go 的 `main` 只调用一个汇编函数。
3. 在 `*_arm64.s` 里实现一个 `Add(a, b int64) int64`，或在 Go 里声明、汇编里实现。
4. 写表驱动测试，至少覆盖正数、负数、零、较大值。
5. 用 `go tool objdump` 确认函数体是你写的指令，而不是 Go 编译器生成的。

### 验收

```bash
go test ./... -count=1     # 通过
go vet ./...               # 无输出
go build -o snake .        # 成功
go tool objdump -s 'goplan9snake/internal/arith\.Add' ./snake | head -30
```

- objdump 输出里能看到 `goplan9snake/internal/arith.Add.abi0` 和你写的 `ADD`/`MOVD` 指令。
- 测试覆盖了负数与边界值。

### 常见坑

- 参数/返回值大小算错（`int64` 每个 8 字节；参数 + 返回值一起算）。
- `FP` 偏移写错；给参数起名后，`go vet` 会帮你检查，但名字必须和 Go 声明一致。
- `go build` 不会检查汇编参数大小；实测把 `$0-8` 写成 `$0-16` 仍能构建，只有 `go vet` 会报 `wrong argument size`。每个里程碑都要跑 vet。
- 漏写 `#include "textflag.h"`，导致 `NOSPLIT` 未定义。
- 使用了 `R18`、`R27`、`R28`、`R29`、`R30`；这些在 arm64 Go 里是保留/特殊寄存器。
- 参考了 Go 1.17 之前的旧博客，看到 `GO_ARGS` 之类写法；现代 Go 通常只需 ABI0 实现 + 编译器生成的 ABI 包装。

## M1 — 汇编基本功：数据、循环、分支、BSS

实现与验收记录：[4.2-FUNDAMENTALS-NOTES.md](4.2-FUNDAMENTALS-NOTES.md)；条目状态见 [2.1-CHECKLIST.md#m1](2.1-CHECKLIST.md#m1)。

### 目标

不依赖任何 Go 逻辑，用汇编实现一批后面会反复使用的纯函数，并建立“汇编函数 + Go 表驱动测试”的工作流。

### 学习点

- `MOVD` / `MOVW` / `MOVWU` / `MOVB` / `MOVBU` / `MOVH` / `MOVHU` 的宽度与符号扩展。
- `ADD` / `SUB` / `MUL` / `UDIV`、移位 `LSL` / `LSR` / `ASR`。
- `CMP` + `BEQ` / `BNE` / `BLT` / `BLE` / `BGT` / `BGE`，以及有符号/无符号比较。
- 内存寻址：`8(R0)`、`(R1)(R2<<2)`。
- `GLOBL`、`NOPTR`、BSS 清零语义；包级符号 `·name(SB)` 跨文件访问。
- `#include "go_asm.h"` 与 `const_Name`。

### 任务

实现并用测试覆盖以下函数：

| 函数 | 用途 |
|---|---|
| `CellIndex(x, y, w int32) int32` | `y*w + x`，供棋盘索引 |
| `Clamp(v, lo, hi int32) int32` | 边界限制 |
| `AbsDiff(a, b int32) int32` | 绝对差（32 位补码回绕契约） |
| `SumTo(n int64) int64` | 循环求和，练分支 |
| `Xorshift64(state uint64) uint64` | 食物随机数 |
| `FillByte(buf *byte, n int32, v byte)` | 帧缓冲/占用数组清零或填充 |
| `Inc() int64` / `Reset()` | 练 BSS 状态与重置 |

要求：

- 每个函数都有表驱动测试或性质测试。
- `CellIndex`、`Xorshift64` 至少跑 100k 组随机输入，与测试文件里的 Go 参考实现对拍。
- BSS 计数器在测试之间通过 `Reset` 清零；测试不要用 `t.Parallel()`（共享 BSS）。
- 不使用 Go 实现作为产品路径的兜底。

### 验收

```bash
go test ./... -count=1
go vet ./...
go build -o snake .
go test -c ./internal/grid -o /tmp/grid.test
go tool objdump -s 'goplan9snake/internal/grid\.CellIndex' /tmp/grid.test | head -20
```

- 所有函数测试通过；随机对拍无差异。
- `Xorshift64(0)` 的边界行为有明确定义（禁止 0 状态，测试覆盖）。
- `FillByte` 能处理 `n == 0`、负 `n`（视为空操作）。

### 常见坑

- 用 `MOVW` 读地址/索引，导致高位被截断；棋盘索引统一用 64 位寄存器更省心。
- 有符号比较用了无符号条件码，或反过来。
- `GLOBL` 的大小写成“元素个数”而不是字节数；`int32` 数组要乘 4。
- 忘记 `#include "go_asm.h"`，把 `const_xxx` 当成符号，报 “illegal or missing addressing mode for symbol”。
- 测试之间 BSS 没清，导致“单独跑通过、一起跑失败”。

## M2 — Darwin 系统调用与终端生命周期

执行条目、顺序和证据见 [2.1-CHECKLIST.md#m2](2.1-CHECKLIST.md#m2)；已冻结契约与草案见 [2.2-CONTRACTS.md](2.2-CONTRACTS.md) §4–§5。

### 目标

用汇编直接和终端/内核打交道：写字节、读窗口大小、睡眠、退出；建立可靠的终端进入/恢复流程。

### 学习点

- Darwin arm64 系统调用约定：`R16` = 系统调用号，`R0`–`R5` = 参数，`SVC $0x80`，carry 表示错误，错误时 `R0` = errno。
- `write` 的短写 / `EINTR` 处理。
- `ioctl(TIOCGWINSZ)` 与 `struct winsize` 布局。
- ANSI：备用屏幕、隐藏/显示光标、光标归位、清屏。
- libSystem 动态导入：在 Go 文件写 `//go:cgo_import_dynamic`，汇编里 `BL libc_usleep(SB)`。
- 为什么裸 `poll/select` 不适合做睡眠（Go runtime 异步抢占导致反复 `EINTR`）。

### 任务

1. 实现系统调用封装（汇编）：
   - `sysWrite(fd, buf, n)`：循环处理短写和 `EINTR`。
   - `sysIoctl(fd, req, arg)`：至少支持 `TIOCGWINSZ`。
   - `sysExit(code)`：直接 `SYS_exit`，不返回。
   - `sleepUS(usec)`：按约 5ms 分片调用 `libc_usleep`；忽略单个分片返回的 -1，按分片递减剩余量。总时长是近似值，被频繁打断时可能略短。
2. 实现 `termSize()`：返回打包的 `rows<<32 | cols`；失败时回退 `80×24`。
3. 实现终端进入/恢复：
   - 进入：备用屏幕 `\x1b[?1049h`，隐藏光标 `\x1b[?25l`，清屏/归位。
   - 恢复：显示光标 `\x1b[?25h`，离开备用屏幕 `\x1b[?1049l`。
4. 写测试/探针：
   - 用 `os.Pipe` 测 `sysWrite` 的字节内容与返回值。
   - 在 pty 下测 `termSize`；非 tty 测回退。
   - 测 `sleepUS(120000)` 的实际耗时在合理范围（例如 100–200ms）。

### 验收

```bash
go test ./... -count=1
go vet ./...
go build -o snake .

# 在真实终端运行 M2-07 的终端探针：进入备用屏幕 -> 横幅 -> 恢复
./snake

# pty 尺寸验证（测试名以实际为准）
# 注意：go test 会给测试进程接管道，必须先编译测试二进制再在 pty 里运行
go test -c -o /tmp/term.test ./internal/term
script -q /dev/null sh -c 'stty rows 40 cols 120; /tmp/term.test -test.run TestTermSize -test.v'
```

- 真实终端：进入备用屏幕，横幅可见，退出后主屏幕内容和光标恢复。
- pty 设为 40×120 时，读到 `rows=40, cols=120`。
- stdout 是管道时，`termSize` 返回回退值且不崩溃。
- `sleepUS(120000)` 实测约 100–200ms（会略短于请求值）；测试断言用 90–300ms 的宽松上界，避免机器负载造成抖动，不出现持续 `EINTR` 死循环。
- `sysWrite` 能处理部分写入（至少代码路径正确，最好有测试）。

### 常见坑

- 系统调用号写成 amd64 的 `0x2000000 + n`；arm64 直接用 `4`、`54`、`1`。
- 忘记 `BCC`/`BCS` 判断 carry；把 errno 当返回值。
- `usleep` 参数是 32 位，写到 64 位寄存器高位的垃圾值可能导致异常。
- `//go:cgo_import_dynamic` 放进 `.s` 文件（它是 Go 编译器指令，应放在 `.go` 文件）。
- 只写一次 `write`，没有处理短写；大帧在 pty 上可能被截断。
- 退出路径没有恢复光标/备用屏幕；`panic`/错误分支也要恢复。
- 直接 `exit` 退出了，但 Go 的 `defer` 不会执行；终端恢复必须在 `sysExit` 之前完成。

## M3 — 游戏状态与移动核心

执行条目、顺序和证据见 [2.1-CHECKLIST.md#m3](2.1-CHECKLIST.md#m3)。

### 目标

在 BSS 中建立完整的蛇状态，用汇编实现移动、吃食物、增长、碰撞和食物生成；先用测试注入方向，不接寻路。

### 学习点

- 扁平索引 `idx = y*W + x`；边界检查。
- 占用位图 `occ[cell]` 与环缓冲 body 的双重表示。
- 环缓冲：`head`/`tail`/`length`/容量；增长时尾巴不动。
- “移动到尾巴格”这一经典例外：尾巴会先让开。
- 随机数 + 线性扫描生成食物，避免接近满盘时的拒绝采样退化。
- 状态机与返回码。

### 任务

1. 定义并初始化 BSS：
   - `W`、`H`、`N=W*H`、`head`、`tail`、`length`、`food`、`rngState`、`status`、`ticks`。
   - `occ`（每格 1 字节）、`body`（每格 4 字节的环缓冲）。
   - 预留 `cycleNext`、`cyclePos`、BFS 队列/首步/访问代数组。
2. 实现 `initGame(w, h, seed)`：
   - 校验尺寸；清 `occ`；长度 1；头/尾在起点；生成第一个食物。
   - 生成/重置随机数状态。
3. 实现 `tickWithDir(dir) int32`：
   - `dir` 来自测试注入（0=上、1=右、2=下、3=左，具体编码自定并固定）。
   - 边界与自撞检查；吃食物/普通移动；更新占用、环缓冲、长度、tick。
   - 返回状态码：`Moved` / `Ate` / `Win` / `Dead`。
4. 实现食物生成：
   - xorshift64 产生随机起点，线性扫描 `N` 格找空位；满盘时返回“无食物”。
5. 实现测试用 getter/setter：
   - `getLength`、`getHead`、`getTail`、`getFood`、`getCell(idx)`、`getBodySlot(i)`、`forceFood(idx)`。
6. 写测试：
   - 直线移动、转弯、撞墙、撞自己。
   - 吃食物后长度 +1、尾巴不动。
   - 普通移动后尾巴让开；移动到尾巴格合法。
   - 环缓冲绕回（构造 head 在末端、再移动）。
   - 食物从不落在蛇身上。
   - 随机方向 fuzz：每次非死亡 tick 后检查不变量。

### 验收

```bash
go test ./... -count=1
go vet ./...
```

- 上述行为测试全部通过。
- fuzz 测试至少 100k 次 tick；每次检查：
  - `occ[i] == 1` 当且仅当 `i` 在 body 的 `length` 个有效槽位中；
  - body 无重复格；
  - 所有格在 `[0, N)`；
  - 食物格空闲；
  - `length` 与有效槽位数一致。
- 吃 10 个食物后长度正确，环缓冲没有越界。

### 常见坑

- 吃食物时把尾巴清了，导致长度不增长。
- 普通移动时先写新头再清尾巴，若新头正好是尾巴格，会把尾巴误判为占用/覆盖。
- 环缓冲容量用 `N`，但满盘后还继续前进；胜利后必须停止。
- 食物生成落在蛇身上，或死循环。
- 32 位索引与 64 位地址混用；`int32` 数组偏移忘记 `<<2`。
- 状态码在不同文件里定义不一致；建议用 Go `const` + `go_asm.h` 统一。

## M4 — 帧渲染与主循环

执行条目、顺序和证据见 [2.1-CHECKLIST.md#m4](2.1-CHECKLIST.md#m4)。

### 目标

把状态渲染成终端画面，建立稳定的帧循环、HUD、终端收尾；先用调试方向模式让蛇动起来。

### 学习点

- 帧缓冲的布局与容量估算。
- 两字符一格的原因（终端字符高宽比）；边框、HUD。
- 整帧一次 `write` 避免闪烁；短写处理。
- ANSI 光标归位 + 覆盖写；备用屏幕。
- 帧率/模拟速率解耦：`renderEvery`、turbo、睡眠分片。
- 汇编里的十进制整数格式化（HUD 需要）。

### 任务

1. 设计帧缓冲：
   - 每格 2 个 ASCII 字符；空、身体、头、食物各自字形。
   - 顶部 HUD（长度/食物数/tick/速度），上下边框，左右边框。
   - 预留足够的 BSS 容量（含 ANSI 转义和终端的最大尺寸）。
2. 实现 `render()`：
   - 构建整帧到 BSS；一次 `sysWrite(1, frame, len)`。
   - 光标归位后覆盖写；必要时清屏。
   - 处理短写/`EINTR`。
3. 实现 `appendUint`（或等价函数）用于 HUD 数字。
4. 实现 `run()` 的调试模式：
   - 终端初始化、尺寸计算、进入备用屏幕。
   - 蛇按一个固定小循环移动（或暂时关闭食物），验证渲染和动画。
   - 退出/失败时恢复终端。
5. 计算棋盘几何：
   - `H = rows - 4`（HUD、上边框、下边框、留一行），向下取偶数。
   - `W = (cols - 2) / 2`，并限制到 `MaxW`。
   - 终端过小时回退到最小尺寸或明确报错。
6. 加帧率控制：模拟速率与渲染频率分离；为 M7 的 turbo 预留参数。

### 验收

```bash
go test ./... -count=1
go vet ./...
go build -o snake . && ./snake
```

- 真实终端中出现完整棋盘：HUD、边框、蛇、食物；尺寸与终端匹配。
- 蛇平滑移动，无整屏闪烁；没有滚屏/错位。
- HUD 的数值正确（长度、食物、tick）。
- 正常退出、调试结束、错误路径都能恢复光标和主屏幕。
- 终端最大/最小尺寸都有明确行为，不越界写帧缓冲。
- `GODEBUG=gctrace=1 ./snake` 在循环期间没有持续 GC（渲染不分配 Go 内存）。
- pty 40×120 下棋盘几何符合公式，没有一行超出宽度。

### 常见坑

- 帧缓冲按“终端字符数”估算，但 ANSI 转义、边框、两字符/格会超出。
- 行尾只写 `\n`，在非 tty 或关闭 OPOST 时没有回车；显式写 `\r\n` 更稳。
- 每帧 `\x1b[2J` 清屏再重画，导致闪烁；优先归位覆盖。
- 终端行数不足，最后一行换行触发滚屏，画面整体上移。
- 只渲染每 tick，导致高频模拟时终端成为瓶颈；要能跳帧。
- 调试模式的食物/增长逻辑与正式逻辑不一致，后面接 M5 时返工。

## M5 — Hamiltonian 环，保证通关

执行条目、顺序和证据见 [2.1-CHECKLIST.md#m5](2.1-CHECKLIST.md#m5)。

### 目标

用 Hamiltonian 环作为安全基线：蛇沿环前进，必然访问所有格子，最终吃光食物并填满棋盘。

### 学习点

- 偶数高度网格上的 Hamiltonian 环构造。
- `cycleNext[cell]` 与 `cyclePos[cell]` 的预计算。
- 环序不变量：蛇身始终是环上的一个前进区间；沿环走不会撞到自己。
- 复杂度：纯环策略虽然保证通关，但填充时间可能是 O(N²)。
- 无头测试：不渲染、不睡眠，快速验证算法。

### 任务

1. 实现环构造（要求 `H` 为偶数，`W >= 2`）：
   - 先沿第 0 列向下；
   - 再在第 1..W-1 列之间按行蛇形往返；
   - 最后从 `(1,0)` 回到 `(0,0)`。
2. 生成 `cycleNext` 和 `cyclePos`；检查首尾相接。
3. 实现 `chooseNextByCycle()`：`next = cycleNext[head]`。
4. 把 `tick()` 接到环策略；保留 `tickWithDir` 供测试。
5. 实现胜利判定与最终帧：
   - 吃到最后一个食物后 `length == N`；
   - 不再生成食物、不再移动；
   - 渲染完整棋盘，停留约 1–2 秒让填满的帧可见；
   - 恢复终端，打印胜利信息并正常收尾。
6. 写测试：
   - 环有效性：N 个格子各访问一次、相邻、首尾相邻、`next`/`pos` 互逆。
   - 无头通关：8×6、16×12、40×20，多个固定种子，断言无死亡且最终 `length == N`。
   - 记录每个尺寸/种子的 tick 数，作为后续混合策略的基线。

### 验收

```bash
go test ./... -count=1
go vet ./...
go test -run 'TestHamilton|TestWin' -v       # 测试名自定
./snake
```

- 环有效性测试通过（所有格子恰好一次、每步曼哈顿距离 1、首尾相邻）。
- 8×6、16×12、40×20 的无头测试都能在预算内通关，无死亡。
- 视觉演示：20×14 左右的棋盘能填满；最后一帧所有格子都是蛇身/头。
- 胜利后不再生成食物、不再写越界；退出码 0。

### 常见坑

- 蛇形方向搞反，最后一格不是 `(1,0)`，环首尾不相邻。
- `cyclePos` 和 `cycleNext` 的初始化漏掉首尾相接。
- H 为奇数时仍按偶数公式构造，导致重复/漏格。
- 初始长度 1 时 head==tail，环序区间定义要特殊处理（M7 会用到）。
- 吃到最后一个食物时还尝试生成食物或继续移动，导致越界。
- 渲染每个 tick 导致 40×20 通关时间过长；无头测试和视觉模式要分开。

## M6 — BFS 寻路（独立验证）

执行条目、顺序和证据见 [2.1-CHECKLIST.md#m6](2.1-CHECKLIST.md#m6)。

### 目标

在静态网格上实现正确的 BFS，返回“从蛇头到目标的第一 step”；先不接入游戏策略，用 Go 参考实现对拍。

### 学习点

- BFS 队列、访问标记、父节点/首步传播。
- 访问代（stamp）避免每次清空 visited 数组。
- 邻居顺序固定，保证结果可复现、可对拍。
- 队列容量：每个格子最多入队一次，容量 N 足够。
- 复杂度 O(N)；在 40×20 上每 tick 一次完全可接受。

### 任务

1. 实现 BFS（输入：起点、目标、占用位图、允许区域/窗口）：
   - 队列数组 + head/tail；
   - `visitedStamp` 用递增的 uint32 代；
   - `firstStep[cell]` 在入队时传播：从起点邻居入队时记该邻居，之后继承前驱的 `firstStep`；
   - 找到目标后返回 `firstStep[target]`，无路径返回 -1。
2. 邻居顺序固定（例如 上、右、下、左），边界检查。
3. 支持“阻塞格”参数：
   - 普通 BFS：`occ != 0` 阻塞；
   - 安全窗口 BFS：额外限制到环序窗口（M7 接入）。
4. 写测试：
   - 小网格手工用例：直线、绕障、无路径、目标在起点、目标被包围。
   - 1000 个随机网格：与测试文件里的 Go BFS 对拍距离/首步。
   - 队列不溢出、访问代不串味、结果确定性。
5. 写 benchmark：40×20、随机障碍、固定种子；记录每 tick BFS 耗时。

### 验收

```bash
go test ./... -count=1
go vet ./...
go test -run 'TestBFS' -v
go test -bench 'BenchmarkBFS' -benchmem
```

- 手工用例全部通过。
- 1000 个随机网格与 Go 参考实现一致（建议固定邻居顺序后比较精确首步）。
- 无路径时返回 -1，不会读写越界。
- 访问代机制正确：连续 BFS 不需要清空 visited。
- benchmark 结果记录在 `docs/` 或注释里；40×20 单次 BFS 耗时在微秒级。

### 常见坑

- 队列用取模环，容量写成 N 但满/空判断差一；其实每格最多入队一次，用线性数组 + head/tail 更简单。
- 起点没有标记 visited，导致重复入队。
- 邻居顺序不固定，测试对拍时结果不稳定。
- 阻塞判断把目标格也阻塞了。
- `firstStep` 在出队时传播而不是入队时传播，导致覆盖/错值。
- 访问代溢出（uint16 太小；用 uint32）。回绕到 0 时要么清空 `bfsStamp`，要么让代值跳过 0。
- 32 位乘法/地址偏移写错。

## M7 — 安全窗口混合策略与性能

执行条目、顺序和证据见 [2.1-CHECKLIST.md#m7](2.1-CHECKLIST.md#m7)。

### 目标

把 BFS 接入游戏：只在 Hamiltonian 环的安全窗口内找捷径，找不到就沿环走；保证不撞、最终填满，并显著快于纯环策略。

### 学习点

- 环序 `pos`、头位置 `hp`、尾位置 `tp`、前向距离。
- 安全窗口：`1 <= forwardDist(hp, c) < forwardDist(hp, tp)`。
- 窗口 BFS：只允许窗口内、未占用的格子；首步即安全捷径。
- 兜底：`cycleNext[head]`；尾巴格特殊处理。
- 不变量：所有蛇身格都在环序区间 `[tp, hp]` 内，头是区间前端。
- 为什么捷径跳过形成的“身后的空隙”最终会被尾巴让出来，不会永久饿死。
- 性能：BFS 每 tick O(N)，纯环 O(1)；用 turbo/跳帧控制视觉时长。

### 任务

1. 实现环序工具：
   - `forwardDist(a, b) = (b - a) mod N`，用条件加减实现，避免除法。
   - 计算 `hp`、`tp`、`distToTail`。
2. 实现安全判定：
   - `length == 1`：任意空闲邻居安全（或直接沿环）。
   - `length > 1`：`1 <= d < distToTail` 的格子在窗口内；
   - 若 `distToTail == 1` 且下一格是尾巴、且不是食物，允许“走进尾巴格”（尾巴会让开）。
3. 实现安全窗口 BFS：
   - 阻塞：`occ != 0`；
   - 区域：窗口内；
   - 目标：食物；
   - 返回首步或 -1。
4. 实现决策顺序：
   - 若食物在窗口内且 BFS 有路：走 BFS 首步；
   - 否则沿环走（处理尾巴特例）；
   - 理论上不需要“追尾巴”兜底，但可以加断言：若环下一格非法，说明不变量被破坏，测试应失败。
5. 在测试里加入不变量检查器：
   - 每 tick 后，所有 body 格子的 `pos` 都在 `[tp, hp]` 前向区间内；
   - 头是区间前端；
   - 无重复、occ 一致。
6. 性能与演示：
   - 实现 turbo：长度/进度超过阈值后，减少渲染频率、缩短/取消睡眠。
   - 记录纯环 vs 混合策略在相同种子、相同尺寸下的 tick 数和 wall time。
   - 设计针对“捷径后食物落在身后空隙”的测试：强制食物在空隙，验证最终能吃到。

### 验收

```bash
go test ./... -count=1
go vet ./...
go test -run 'TestHybrid|TestInvariant|TestWin' -v
go test -bench 'BenchmarkBFS' -benchmem
./snake
```

- 每个 tick 后不变量成立（至少 20 个种子 × 50k tick 的长跑）。
- 40×20 固定种子全部无死亡并最终通关；记录 tick 预算并在测试中断言。
- 相同种子下，混合策略比纯环策略显著更快（建议目标 ≥2×，以实测为准）。
- 针对“食物在身后空隙”的测试通过：蛇不死亡，最终吃到该食物。
- 视觉演示中能看到捷径（不是全程机械沿环），且没有撞墙/自撞。
- turbo 模式下全屏填满的 wall time 可接受；把实测数据写入 `docs/5.1-PERF.md`。

### 常见坑

- `forwardDist` 在 `a == b` 时返回 0，`length == 1` 时窗口为空；必须特判。
- 计算窗口时把尾格包含进去，或把窗口端点算反。
- BFS 允许了窗口外的格子，导致捷径越过头/尾，破坏不变量。
- 尾巴格在 BFS 里被当阻塞，导致唯一合法走法被漏掉；需要兜底/特判。
- 食物在身后空隙时误判“无解”并停住；实际上应继续沿环，等尾巴让开。
- 增长时尾部不动，窗口端点不变，但头前进了；不变量检查要覆盖吃食物这一步。
- turbo 只减少睡眠、不减少渲染，终端仍可能成为瓶颈；两者都要调。
- 长跑测试没有 tick 上限，算法 bug 时测试挂死；所有长跑都要有预算断言。

## 交付与常见全局问题

每轮按 [AGENTS.md](../AGENTS.md)「一轮会话流程」推进；里程碑关卡见 [2.1-CHECKLIST.md](2.1-CHECKLIST.md) 的 `M*-G1` 条目，代码边界见 [2.2-CONTRACTS.md](2.2-CONTRACTS.md) §2.2。

- **调试顺序**：先写纯函数 + 表驱动测试（M1），再写状态机 + 不变量 fuzz（M3），随后接独立算法对拍（M5/M6/M7），最后接全屏渲染循环（M4/M8）；不要一上来在全屏循环里调寻路。
- **性能与正确性**：先保证不变量和确定性通关，再开启 turbo/跳帧；所有优化均需对拍或 benchmark 数据支撑。
- **终端异常恢复**：若进程异常中断导致停留在备用屏幕或光标隐藏，在终端执行：

```bash
tput rmcup   # 离开备用屏幕
tput cnorm   # 恢复光标
reset        # 兜底重置
```
