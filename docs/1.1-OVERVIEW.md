# 实现总览

本文用通俗语言说明这个自动贪吃蛇的实现方案和函数职责，不包含 Go 或汇编实现代码。技术论证见 [3.1-DESIGN.md](3.1-DESIGN.md)，里程碑目标见 [1.2-ROADMAP.md](1.2-ROADMAP.md)，条目顺序与状态见 [2.1-CHECKLIST.md](2.1-CHECKLIST.md)，精确契约见 [2.2-CONTRACTS.md](2.2-CONTRACTS.md)；本文只回答“这个函数是做什么的、写它时要注意什么”。

> 状态（2026-11-23）：M0、M1 已完成；M1 函数均已实现并验收，位于 `internal/arith`、`grid`、`rng`、`mem`、`counter`。M2 起为计划；当前条目见 [2.1-CHECKLIST.md](2.1-CHECKLIST.md)。

> 核心心智模型：程序维护一份棋盘状态，每个 tick 让蛇前进一格，再按固定节奏把整份状态重新画到终端。每个函数基本只做三件事之一：改状态、根据状态做决策、把状态画出来。

---

## 一、程序从启动到退出

```text
启动
  ↓
问终端：现在几行几列？
  ↓
算棋盘：宽多少、高多少（高度必须是偶数）
  ↓
初始化：清空棋盘、放蛇、放第一颗食物
  ↓
进入备用屏幕（一块临时画布，退出后原终端恢复原样）
  ↓
循环：
    选下一步方向
      ↓
    走一格（普通移动 / 吃到 / 胜利 / 死亡）
      ↓
    到了该画的时候：拼一整帧 → 一次写到终端
      ↓
    睡一小会儿
  ↓
填满棋盘（或出错）
  ↓
恢复光标和终端 → 打印结果 → 退出
```

这里有两个容易被忽略、但很关键的点：

1. **“走一步”和“画一帧”不是一一绑定的。** 蛇可以走得比画面快，渲染可以跳帧；后期加速时正是靠这一点。
2. **退出前必须恢复终端。** 直接退出进程不会执行任何 Go 的清理逻辑，所以所有退出路径都要先把光标和主屏幕恢复好。

## 二、先懂这 6 个数据概念

### 1. 棋盘是“一根长条”，不是二维表

每个格子有一个编号：

```text
编号 = 行号 × 棋盘宽 + 列号
```

所有数组都只需要“编号”一个下标。上下移动是加减棋盘宽，左右移动是加减 1，但**必须额外检查有没有跨行**，不能只看编号在不在范围内。

方向约定建议固定为“上、右、下、左”；一旦定下，整个项目统一使用。

### 2. 占用表：每格一个字节

它只回答一个问题：**“这一格现在有没有蛇？”**

- 碰撞检查靠它。
- 食物能不能放这里靠它。
- 它查询快，但不知道蛇身的顺序，也不知道哪一节是尾巴。

### 3. 身体队列：一圈槽位，记蛇身顺序

它按顺序保存蛇身每一节的格号，并且只维护两个指针：头槽位和尾槽位。

- 普通移动：头往前占一个新槽，尾巴腾出旧槽。
- 吃到食物：头往前占新槽，尾巴不动。
- 槽位走到头就绕回 0，所以叫“环缓冲”。

**为什么用环缓冲？** 蛇的移动本质是“进一节、出一节”，不需要把整条蛇往后搬。容量最大就是棋盘格数。

**为什么占用表和身体队列都要有？** 一个负责快速回答“这里有没有东西”，一个负责顺序、尾巴和增长。两者必须始终同步，这是整个项目最重要的不变量。

### 4. 食物和随机数

- 食物就是一个格号；`-1` 表示当前没有食物。
- 随机数状态是一个全局数。
- 生成食物时：先随机一个起点，再从起点沿棋盘扫一圈，找到第一个空格。
- 为什么不用“随机抽到空为止”？因为接近满盘时，随机可能抽很久都抽不到；线性扫描最多走 N 步必有结果。

### 5. 环和寻路辅助表

- **环**：给每个格子记两条信息——环上的下一格是谁、它在环上排第几。
- **BFS 辅助表**：一个队列、每个格子的“第一步”、以及一个“访问代”标记。这些表每 tick 复用，不重新分配。

### 6. 帧缓冲

一整块提前分配好的字符画布。渲染就是往上面拼文字，最后**一次性**写到终端，而不是每格写一次。

## 三、函数地图：每个函数是干什么的

> 下面的函数名是概念名，不是冻结签名；精确契约以 [2.2-CONTRACTS.md](2.2-CONTRACTS.md) 为准，顺序和状态以 [2.1-CHECKLIST.md](2.1-CHECKLIST.md) 为准。一旦定了，状态码、方向编码和格号定义就要全局统一。

### M1：基础工具（已完成）

| 函数 | 它负责什么 / 写的时候记住 |
|---|---|
| **CellIndex(列, 行, 宽)** | 把坐标换成一维编号：行 × 宽 + 列。所有位置计算的地基；x 是列、y 是行，别写反。 |
| **Clamp(值, 下限, 上限)** | 把数值夹到区间内。主要用于尺寸和边界计算；上下限颠倒时返回上限。 |
| **AbsDiff(a, b)** | 两个数的绝对差。采用 32 位补码回绕契约；注意最小负数取绝对值会回绕。 |
| **SumTo(n)** | 从 1 加到 n。纯练习循环和分支，**不进入游戏路径**。 |
| **Xorshift64(状态)** | 输入当前随机状态，返回下一个随机值，这个返回值同时作为下一次的状态。状态 0 会永远输出 0，种子 0 要换成非零常数。 |
| **FillByte(缓冲区, 长度, 值)** | 把连续一段内存全部填成同一个字节。用来清占用表或铺帧缓冲；长度 0 或负数视为空操作。 |
| **Inc / Reset** | 全局计数器加一 / 清零。这是练 BSS 全局状态的练习，不是游戏核心；测试之间必须 Reset，且不能并行跑。 |

### M2：终端与系统调用

| 函数 | 它负责什么 / 写的时候记住 |
|---|---|
| **sysWrite(描述符, 缓冲区, 长度)** | 把一段字节完整写到终端。要处理“只写了一半”和“被信号打断”的情况。所有可见输出都走它。 |
| **sysIoctl(描述符, 请求, 参数)** | 向系统询问终端信息，主要是窗口的行数和列数。结果写在固定 8 字节内存里；不是终端时会失败。 |
| **termSize()** | 把终端行列打包成一个数返回；失败时回退 80×24。启动时算棋盘几何的依据。 |
| **sleepUS(微秒)** | 近似睡指定时长，切成约 5ms 一小片调用系统睡眠。不要用裸 poll/select，Go 的抢占会反复打断它。 |
| **sysExit(码)** | 立刻结束进程，不执行任何 Go 清理。**调用前必须已经恢复终端。** |
| **进入/恢复终端** | 进入备用屏幕、藏光标、清屏归位；退出时显示光标、回主屏幕。正常、胜利、失败路径都要恢复。 |

### M3：游戏状态与移动

| 函数 | 它负责什么 / 写的时候记住 |
|---|---|
| **initGame(宽, 高, 种子)** | 整局重置：校验尺寸、清空占用表、蛇长设为 1、头尾同格、重置随机状态、放第一颗食物。每个测试开头都要调用。 |
| **tickWithDir(方向)** | 按指定方向走一步，是移动逻辑的唯一入口，也是测试接缝。负责撞墙/自撞检查、吃没吃判断、更新占用/身体/长度/tick，返回状态码。 |
| **自动 tick** | 先让策略选出方向，再走和 tickWithDir 同一套移动逻辑。不要把移动逻辑复制两份。 |
| **spawnFood()** | 随机起点，沿棋盘扫一圈找第一个空格放食物。蛇占满时表示没有空位；食物绝不能落在蛇身上。 |
| **getters 一族** | 只读查询：长度、头、尾、食物、某格占用、某身体槽位、环位置、状态、tick。给测试观察用；因为状态都在全局内存里，这些查询也在汇编。 |
| **forceFood(格号)** | 测试专用：把食物强行放到指定格，用来复现“食物在身后空隙”之类的场景。 |
| **状态码** | 四个结果：普通移动、吃到、胜利、死亡。主循环靠它决定继续、收尾还是报错；集中定义常量，别散落魔数。 |

**一次移动的更新顺序是这里最容易错的地方：**

- 普通移动：**先让尾巴腾出旧格，再写新头**。因为新头可能正好是尾巴格；顺序反了会把尾巴误判成身体。
- 吃到食物：**不能清尾巴**，否则长度不会增长。
- 吃到最后一个食物、长度等于棋盘格数时：立刻返回胜利，不再生成食物、不再移动。

### M4：渲染与主循环

| 函数 | 它负责什么 / 写的时候记住 |
|---|---|
| **棋盘几何计算** | 由终端行列算棋盘宽高：扣掉 HUD 和上下边框，高度向下取偶数；宽度按每格 2 个字符计算；再限制最大尺寸。太小要有回退或明确报错。 |
| **render()** | 把 HUD、边框、每个格子的两个字符拼进帧缓冲；光标归位后一次写出。不逐格写、不每帧清屏，这是不闪烁的关键。 |
| **appendUint(值)** | 把整数转成十进制文本，给 HUD 显示用。汇编里没有 fmt，这是替代品。 |
| **run()** | 总调度：初始化终端和游戏，循环“决策 → 移动 → 偶尔渲染 → 睡眠”，最后收尾。正常和异常退出都要恢复终端。 |

**为什么每格两个字符？** 终端字符通常“高比宽大”，一个字符画出来是竖长条；用两个字符一格，棋盘看起来才接近正方形。每个字形宽度固定为 2，几何才不会错位。

### M5–M7：自动寻路

| 函数 | 它负责什么 / 写的时候记住 |
|---|---|
| **构造环** | 在所有格子上构造一条闭合环路，填好“下一格”和“环上序号”。高度必须是偶数；每格恰好访问一次，首尾要相接。 |
| **chooseNextByCycle()** | 返回环上头部的下一格。最保守、可证明安全的走法。 |
| **forwardDist(A, B)** | 环上从 A 向前走到 B 需要几步（绕回也算）。用条件加减实现，不做除法；A 等于 B 时结果是 0。 |
| **安全窗口判定** | 只允许走“头部前方、尾巴之前”的格子。长度 1 时窗口为空，要特判；下一格正好是尾巴时也要特判允许。 |
| **bfs(起点, 目标, 阻塞条件)** | 在空闲格中找从蛇头到食物的最短路径，只返回**第一步**。用队列、访问代和第一步传播；邻居顺序固定，保证结果可复现。 |
| **chooseNext()** | 自动玩的核心决策：食物在安全窗口内且 BFS 有路，就走 BFS 的第一步；否则沿环走。BFS 只负责加速，环负责保命。 |
| **tick()** | 决策 + 移动的组合。测试仍然可以绕过决策，用 tickWithDir 直接注入方向。 |

**BFS 的“第一步”怎么来的？** 从蛇头往外一层层扩散时，蛇头的邻居各自记下“我是从蛇头的哪个方向来的”；更远的格子继承它上一层邻居的记录。所以找到食物时，不需要回溯整条路径，直接读食物格上记录的“第一步”即可。

**“访问代”是什么？** 每格有一个数字标记。每次 BFS 换一个新的代数，只有标记等于当前代的格子才算访问过。这样不用每次把整张访问表清零。

## 四、一次 tick 到底发生了什么

按顺序记这个流程：

1. 看当前状态：头在哪、尾在哪、蛇多长、食物在哪。
2. 让策略选下一步：BFS 捷径，或者环的下一格；测试时可以直接指定方向。
3. 检查目标格：
   - 出界 → 死亡。
   - 是身体格 → 死亡。
   - 正好是尾巴格，且这次是普通移动 → **允许**，因为尾巴下一步会让开。
4. 判断这一步是不是吃到食物。
5. 更新状态：
   - 普通移动：清掉旧尾，写入新头，头尾槽位都前进。
   - 吃到：写入新头，尾巴不动，长度加一，重新生成食物。
   - 如果长度等于棋盘总格数 → 胜利，停止。
6. 同步更新占用表、tick 计数、状态码。
7. 主循环根据状态码决定：继续、渲染、胜利收尾，还是报错收尾。

## 五、最绕的算法，用一句比喻讲清楚

把棋盘想成一条**串起所有座位的单向环形传送带**：

- 蛇是传送带上的一个车队，车头在前、车尾在后，车身永远占据连续的一段路。
- 只沿传送带走，车头前面要么是空路，要么正好是车尾——而车尾下一步就会离开，所以永远不会撞到自己。
- 因为传送带经过每一个座位，食物迟早会被吃到，最后整个棋盘被填满。
- 缺点是慢：纯环策略最坏要走 O(N²) 步。

BFS 是“抄近道”：

- 只允许在**车头前方、车尾之前**这段空路里找捷径。
- 绝不越过车尾，否则等于把自己的退路截断。
- 抄近道会在身后留下一些空格；食物如果刷在那里，当前窗口看不到，就继续沿环走。车尾不断前进，等车尾越过那个空格，它就进入安全窗口，之后自然能吃到。
- 所以最短也是沿环走，不会永久卡死；最坏情况退化成纯环策略，仍然保证通关。

**尾巴格特例：** 当车头前方紧挨着车尾时，安全窗口里没有格子，但尾巴下一步会让开，所以允许走进尾巴格。这个特例只在“不是吃食物”时成立；而食物本来就不会刷在蛇身上。

## 六、写代码时随身检查的不变量

这些是 [3.1-DESIGN.md](3.1-DESIGN.md) 里测试要反复验证的东西，也是调 bug 时的第一反应：

- 所有格号都在 `0` 到 `N-1` 之间。
- 占用表为“有蛇”的格子集合，和身体队列里的有效格子集合完全一致。
- 身体队列里没有重复格。
- 长度等于有效槽位数，且不超过总格数。
- 食物要么是 `-1`，要么是一个占用为空的格子。
- 普通移动后尾巴前进一格；吃食物后尾巴不动、长度加一。
- 长度等于总格数时立刻胜利，之后不再移动、不再生成食物。
- 纯环或混合策略下，所有身体格都在环上“从尾到头”的前向区间里，头在最前。
- 所有长跑测试都要有 tick 上限，算法出 bug 时测试不能挂死。
